# RoboBrain2.5 视觉 Token 裁剪阶段汇报

日期：2026-09-16  
模型：RoboBrain2.5-4B  
任务：图像目标定位（Grounding）和目标中心指点（Pointing）  
当前进度：Token 裁剪的软件研究暂时停止，FPGA Selector 暂不实现

## 1. 我们为什么要做 Token 裁剪

### 1.1 问题从异构平台选型开始

RoboBrain2.5-4B 不能把原始 BF16 模型完整放进 ZCU102 的片上存储。BF16 是每个数使用 16 bit 的浮点格式，完整模型权重约 9 GB，远大于 ZCU102 的片上存储。完整推理也不适合全部交给 ZCU102。前期平台调研后，我们形成的系统设想是：主 AI 平台负责视觉编码、语言模型 Prefill 和自回归 Decode，ZCU102 负责适合定制流水线的预处理、局部视觉选择、结构化输出或安全控制。Prefill 指模型第一次并行处理全部文本和视觉输入；Decode 指此后逐个生成输出 Token 的过程。

视觉 Token 裁剪是这个系统设想中的一个候选功能。它希望在模型继续推理之前删掉不重要的图像信息，从而减少后续视觉编码和语言模型处理的序列长度。

这里的 **视觉 Token** 可以理解为图像被模型切成小块后，每个图像块对应的一条特征向量。RoboBrain 使用的 Qwen3-VL 会先把图像分成 patch，再通过视觉编码器提取特征，并把相邻 patch 合并成送入语言模型的视觉 Token。Token 越多，后续 Attention、MLP 和语言模型 Prefill 的计算量通常越大。

### 1.2 我们要验证的不是“能不能删除 Token”

删除 Token 在程序上并不困难，真正的问题是：

> 能否在 Grounding 和 Pointing 的精度基本不下降的前提下，把视觉 Token 数量和实际计算量降下来，并且让节省的时间大于选择 Token、传输数据和重新组织序列所产生的开销？

这个问题包含四个同时成立的条件：

1. **保留任务需要的信息。** 目标轮廓、边缘、小物体和操作位置不能被误删。
2. **确实减少计算。** 不能只让最终 Token 数变少，而前面的视觉层仍然处理完整图像。
3. **选择过程足够便宜。** 如果先运行一个很重的模型来判断哪些 Token 重要，节省的计算会被选择器消耗掉。
4. **适合异构实现。** 不能为了选择 Token 频繁执行 GPU→FPGA→GPU 往返。

### 1.3 本阶段设定的目标

我们先把 Dense 原始推理作为基线。**Dense** 表示不裁剪 Token，视觉编码器和语言模型按原始完整序列运行。

阶段目标分为两档：

- **轻度裁剪目标**：先判断保留 87.5% Token 时，空间任务精度能否保持稳定。
- **激进裁剪目标**：进一步判断能否把最终视觉 Token 压到 Dense 的 50% 以下，同时保持 Grounding 和 Pointing 的主要指标基本不下降。

只有软件实验同时通过精度、计算量和延迟门槛后，才值得把 Token 选择器做成 ZCU102 上的 RTL/HLS 模块。RTL 是寄存器传输级硬件设计；HLS 是用 C/C++ 等高级语言生成硬件电路的设计方法。

## 2. 我们尝试了哪些方法

### 2.1 统一降低图像分辨率

最简单的办法是把整张图像缩小。图像长宽变小后，patch 和视觉 Token 数自然下降。

这种方法保留了完整画面，但小目标、边缘和细节会一起变模糊。它是必须比较的基础方法，不是本项目的创新算法。

### 2.2 使用真值框裁出目标区域

**ROI** 是 Region of Interest，即“感兴趣区域”。ROI 裁剪只保留目标附近的一块连续矩形图像，再把该区域缩放到模型输入尺寸。

本阶段使用的 **真值 ROI** 是直接读取 COCO 数据集人工标注的目标框，在目标框周围保留一定上下文后裁图。因为实际部署时不可能提前知道正确目标框，所以真值 ROI 不能部署。它的作用是给出一个上界：如果已经知道目标在哪里，只处理目标附近的连续图像区域，理论上能达到什么效果。

真值 ROI 和普通 Token 删除的区别是：

- Token 删除是在特征序列中留下若干离散位置；
- ROI 保留的是一块连续图像，目标会被重新采样和放大，局部二维结构仍然完整。

### 2.3 在视觉编码器中间按 L2 分数保留 Token

报告中的 **L2@87.5%** 是一条具体算法配置，不是一个通用名词：

1. 图像先正常通过视觉编码器第 0 至第 5 层，也就是前 6 个视觉块。
2. Qwen3-VL 的 `spatial_merge_size=2`，相邻 `2×2` patch 会组成一个 merger group。选择器以这样的 group 为最小保留单位。
3. 对每个 group 的特征向量计算 L2 范数：

   `L2 = sqrt(x1² + x2² + ... + xd²)`

   数值越大，表示该特征向量的整体响应越强。我们把它当作“可能更重要”的简单近似。
4. 按分数选择 group，最终保留原数量的 87.5%，所以写作 `L2@87.5%`。
5. 第 6 至第 23 层以及后续语言模型只处理保留下来的 group。

为了防止高分 Token 全部集中在某一小块区域，算法还加入了 **3×3 区域锚点约束**。实现并不是固定保留九个中心点，而是：

1. 把二维特征网格最多划分成 3 行×3 列的粗区域；
2. 每个区域先保留一个 L2 分数最高的 group，保证画面各区域至少有一个代表；
3. 剩余名额再按照全图 L2 分数从高到低填满。

因此，`L2@87.5% + 3×3 anchor` 的完整含义是：**在第 5 层之后，以 2×2 patch group 为单位，先保证粗粒度空间覆盖，再按特征 L2 强度补足，最后保留 87.5% 的视觉 group。**

### 2.4 在 L2 基线上训练小型选择器

L2 只反映特征强度，不知道用户问的是哪个目标。我们随后尝试了两类小型学习器：

- **残差选择器**：以 L2 分数为基础，学习一个小修正量；
- **联合删除选择器**：不再只评价单个 Token，而是学习删除多个 Token 后对坐标输出的共同影响。

这样设计是为了让选择器具有任务感知能力，同时保持计算规模足够小，便于以后映射到 FPGA。

### 2.5 在不同位置执行裁剪

我们测试了五个裁剪位置：patch embedding 后、视觉 block1 后、block3 后、第一次 DeepStack 注入附近的 layer5 后，以及视觉 merger 后。Patch embedding 是把图像块转换为特征向量；视觉 block 是视觉 Transformer 的一层；merger 负责把相邻视觉特征合并后交给语言模型；DeepStack 是模型把多层视觉特征注入语言模型的机制。

越早裁剪，后续少算的层数越多，但早期特征语义较弱；越晚裁剪，特征更容易判断目标，却已经消耗了大部分视觉计算。这项实验用于寻找精度和计算收益之间的平衡点。

### 2.6 在真实 Q8 模型中实现动态 Token 压缩

为了确认方法不仅能在 BF16 的 Hugging Face 模型里运行，我们在真实 GGUF Q8_0 模型中实现了两条路径：

- **Q8-A**：在视觉 merger 之后压缩，只减少送入语言模型的视觉 Token；
- **Q8-B**：在视觉 block1 之后压缩，使后续视觉层也处理更短的序列。

这里的 Q8_0 是权重采用 8 位量化的模型格式。Q8-A 和 Q8-B 是本项目对两个插入位置的编号，不是业界标准算法名称。

### 2.7 用连续矩形 ROI 替代离散 Token 删除

前面的实验提示，离散删除可能破坏二维连续性。因此我们改为保留完整矩形区域，并比较两种处理分辨率：

- `ROI-384`：把裁出的矩形区域按长边 384 送入模型；
- `ROI-512`：把裁出的矩形区域按长边 512 送入模型。

分辨率越高，目标细节越清楚，但 Token 数和计算量也越大。我们还计算了一个逐图“理想选择”上界：每张图根据真实答案选择 384 或 512 中效果更好的一个。这个选择使用了真值，只能说明动态分辨率是否值得研究，不能用于部署。

### 2.8 在相同 Token 预算下比较 ROI 和离散裁剪

为了排除“ROI 只是用了更多 Token”的影响，我们让每个样本的 ROI 和 layer5 L2 最终保留完全相同数量的 Token，再比较任务精度。

此外还设计了一个 **几何 Oracle**：它直接读取真实目标框，优先保留与目标框相交的视觉网格，然后保留周围上下文。Oracle 在这里指使用实际部署时不可获得的正确答案，构造一个理想条件下的性能上界。它比 L2 更清楚目标在哪里，但仍然使用离散 Token。这个实验用来回答：离散裁剪失败究竟是因为没有选中目标，还是因为离散表征本身存在问题。

### 2.9 用低分辨率图像预测 ROI

真值 ROI 不能部署，所以最后尝试了一个低成本的自动定位流程：

1. 把完整图像缩小到长边 256；
2. 只运行视觉编码器前 6 层；
3. 根据图像特征和任务文本预测目标热力图与矩形大小；
4. 如果定位可靠，再读取高分辨率 ROI 进行正式推理。

这个低成本前置定位器在报告中称为 **Scout**，即先进行一次粗略观察。我们分别测试了文本与图像特征余弦相似度，以及岭回归热力图加尺度预测头。

## 3. 我们如何判断裁剪有没有用

### 3.1 两项空间任务

本阶段没有使用一般图像描述作为主要精度标准，而是选择了对空间信息更敏感的任务。

**Pointing（目标中心指点）**：给出图像和目标类别，要求模型输出目标中心点 `(x, y)`。坐标统一归一化到 0–1000。

**Grounding（目标框定位）**：给出图像和目标类别，要求模型输出目标边界框 `[x1, y1, x2, y2]`，坐标同样归一化到 0–1000。

Pointing 和 Grounding 都使用 COCO 人工标注作为真值。COCO 中的框中心只能代表目标中心，不能等同于抓取点、杯把位置或机器人可供性点。

### 3.2 Pointing 使用的指标

先计算模型预测点和真实目标中心之间的欧氏距离，再除以真实目标框的对角线长度：

`归一化误差 = 预测点与真实点的距离 / 真实目标框对角线长度`

使用目标框对角线归一化，是为了避免同样的像素误差对大目标和小目标产生不公平影响。

- **PCK@0.1**：PCK 是 Percentage of Correct Keypoints，即“正确关键点比例”。PCK@0.1 表示归一化误差不超过 0.1 的样本比例，可以理解为预测误差没有超过目标框对角线的 10%。数值越高越好。
- **PCK@0.2**：误差不超过目标框对角线 20% 的样本比例，要求比 PCK@0.1 宽松。数值越高越好。
- **NME**：Normalized Mean Error，归一化平均误差。它保留连续误差信息，数值越低越好。

例如 PCK@0.1=0.60，表示 60% 的样本把目标点预测到了“距离真实中心不超过目标框对角线 10%”的范围内。

### 3.3 Grounding 使用的指标

**IoU** 是 Intersection over Union，即预测框与真实框的交并比：

`IoU = 预测框与真实框的交集面积 / 两个框的并集面积`

IoU 的范围是 0 到 1。两个框完全重合时为 1，完全不相交时为 0。

- **Mean IoU**：所有样本 IoU 的平均值，越高越好。
- **Acc@0.5**：Acc 是 Accuracy，即准确率。Acc@0.5 表示 IoU 不低于 0.5 的样本比例，越高越好。

例如 Acc@0.5=0.88，表示 88% 的样本达到了 IoU≥0.5。

### 3.4 输出格式和统计指标

- **格式解析成功率**：模型输出能否严格解析成一个点或一个框。解析失败的样本按精度失败处理。
- **95% 置信区间**：对同一批图片上的候选方法与 Dense 差值进行 10,000 次配对 bootstrap。Bootstrap 是从现有配对样本中反复有放回抽样，用来估计结果波动范围。区间跨过 0 说明当前数据不足以证明改善或退化，不能写成“无损”。
- **p50 延迟**：一半请求快于这个值，也就是延迟中位数。
- **p95 延迟**：95% 请求快于这个值，用于观察长尾延迟。

### 3.5 计算量指标

- **Token 比**：候选方法最终视觉 Token 数除以 Dense Token 数。例如 0.342 表示最终只保留 Dense 的 34.2%。
- **Vision MAC 代理比**：MAC 是 Multiply-Accumulate，即一次乘法加一次累加。该指标根据各视觉层实际处理的序列长度，估算主要矩阵乘加运算量相对 Dense 的比例。它不等同于板端实测时间。
- **LLM Prefill MAC 比**：语言模型第一次读取全部文本和视觉 Token 时，主要矩阵运算量相对 Dense 的比例。
- **累计视觉 Token**：包含 Scout、ROI 重编码等所有步骤实际处理过的 Token。不能只报告最后一次输入的 Token 数。

### 3.6 进入下一阶段的门槛

扩大数据后的预设工程门槛是：

- 相对 Dense，PCK@0.1 和 Mean IoU 的下降均不超过 0.02；
- 格式解析成功率下降不超过 0.01；
- 平均累计视觉 Token 不超过 Dense 的 50%；
- 模型 p50 延迟至少下降 20%，p95 不恶化。

这些是继续进入校准集和测试集的条件，不是已经达到的结果。

## 4. 实验具体怎么做

### 4.1 数据逐步扩大，而不是一直使用最初四张图片

研究过程使用了多级数据集：

1. 最初小样本只用于检查程序接口和明显错误，不用于精度结论。
2. 第一轮 Pareto 实验使用 32 张 COCO 图像，每张同时生成 Pointing 和 Grounding 请求。
3. L2 冻结方法使用与开发数据隔离的 96 图盲集，比较 Dense、L2 和学习式选择器。
4. 后续重新选择 800 张此前从未使用的 COCO 2017 validation 图像，划分为开发 192、校准 96、测试 512。
5. 三个新划分彼此不重叠，并且与 432 张历史实验图像零重叠。

目前 192 图开发集已经用于方法分析；96 图校准集和 512 图测试集仍然封存。因为当前方法没有通过开发门槛，所以没有为了得到更多数字而提前打开测试集。

### 4.2 先验证不裁剪路径完全一致

每种动态裁剪实现都必须先在 100% 保留时与原始模型比较。只有输出 Token ID 或最终文本完全一致，才能说明插入裁剪接口没有改变原始模型语义。

已完成的主要一致性检查包括：

- BF16 浅层裁剪 100% 路径：64/64 输出一致；
- Q8-A 100% 路径：Token ID 完全一致；
- Q8-B 100% 路径：输出一致；
- ROI/L2 同预算实验修正 processor 边界后：自定义 Dense 与原生 Dense 384/384 输出逐字一致。

### 4.3 L2 基线的执行位置

RoboBrain 视觉编码器共有 24 层。L2 基线让前 6 层处理完整图像，在第 5 层输出后选择 `2×2` patch group；剩余 18 个视觉层和 LLM Prefill 只接收保留 group。保留的 Token 继续沿用原始 RoPE/MRoPE 位置编号，不重新连续编号。RoPE 是旋转位置编码，MRoPE 是面向多模态位置的扩展；它们告诉模型每个 Token 原来位于图像和序列的什么位置。

### 4.4 ROI 的坐标处理

ROI 方法先按原图像素裁出连续矩形区域，再按 384 或 512 长边缩放。模型输出的是相对 ROI 的 0–1000 坐标，主机根据实际整数像素裁剪框，把坐标映射回原图。所有 PCK 和 IoU 都在原图坐标系下计算。

### 4.5 自动 ROI 定位器的验证方式

低分辨率 Scout 使用 192 张开发图、384 个任务样本，并按“图像”进行 5 折交叉验证。同一张图片的 Pointing 和 Grounding 记录不会被分到训练折和验证折两边，避免图像泄漏。

在运行完整 4B 模型之前先检查四项门槛：目标中心召回、目标框覆盖率、Token 比和累计 Vision MAC。定位门失败后，不再继续执行昂贵的完整 VLM 生成。

### 4.6 延迟测量范围

GPU 正式计时在模型加载后进行，先 warmup，再重复测量，并在 GPU 计时段前后执行 `torch.cuda.synchronize()`。阶段时间区分 Vision、LLM Prefill 和 Decode。

报告中的平台传输时间仍是带宽模型估算，不是目标异构平台实测。JPEG 解码、Resize、归一化、布局变换和设备传输只有在同一应用计时边界内测量时，才计入应用端到端延迟。

## 5. 实际测到了什么

### 5.1 只缩小整张图，Token 越少，空间精度越差

在 32 张图的第一轮实验中，统一缩放后的实际 Token 比依次约为 0.677、0.459、0.239 和 0.100。随着图像继续缩小，Pointing 和 Grounding 总体持续下降。

当 Token 预算都约为四分之一时：

| 方法 | 实际 Token 比 | PCK@0.1 | PCK@0.2 | Mean IoU | Acc@0.5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 统一缩小整图 | 0.239 | 0.3438 | 0.6875 | 0.6274 | 0.6875 |
| 真值 ROI | 0.246 | 0.5312 | 0.8125 | 0.7545 | 0.8750 |

两者 Token 数几乎相同，但真值 ROI 的四项指标分别高出 0.1875、0.1250、0.1271 和 0.1875。这说明：**决定精度的不只是保留多少 Token，还包括保留的是哪块区域，以及是否保持了连续图像结构。**

### 5.2 轻度 L2 裁剪可以保留为基线，但没有证明完全无损

在新的 96 图盲集上，每张图分别执行 Pointing 和 Grounding，并比较三种方法，共 576 条推理。

| 方法 | Token 比 | Vision MAC 比 | LLM Prefill MAC 比 | PCK@0.1 | PCK@0.2 | Mean IoU | Acc@0.5 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| Dense，不裁剪 | 1.000 | 1.000 | 1.000 | 0.5729 | 0.7708 | 0.7804 | 0.8854 |
| L2@87.5% + 3×3 区域锚点 | 0.875 | 0.897 | 0.873 | 0.5833 | 0.8125 | 0.7840 | 0.8854 |
| L2 加学习式残差选择器 | 0.875 | 0.897 | 0.873 | 0.5729 | 0.7917 | 0.7819 | 0.9062 |

L2 的点估计没有比 Dense 差，但这不足以证明统计意义上的无损。学习式残差选择器也没有稳定超过 L2，所有“学习式选择器减去 L2”的 95% 置信区间都跨过 0。

后续联合删除选择器虽然在开发数据的坐标损失上有改善，但真正生成坐标后使 Pointing PCK@0.1 下降。换到新的 96 图测试时，任务路由仍未改善任何主要指标。因此我们停止这两种学习式选择器，把 L2@87.5% 留作轻度裁剪基线。

### 5.3 真实 Q8 模型证明接口可用，但精度没有通过

Q8-A 在 merger 后保留 75% Token：

- 视觉 Token 从 176 降到 132；
- 8/8 输出都能解析；
- Grounding Mean IoU 从 0.7701 变为 0.7799；
- Pointing PCK@0.1 从 0.75 降到 0.50。

Q8-B 在 visual block1 后保留 87.5% Token：

- group 从 176 降到 154；
- 后续视觉 patch 行从 704 降到 616；
- Grounding Mean IoU 从 0.7701 变为 0.7993；
- Pointing PCK@0.2 从 1.00 降到 0.75。

这两次实验的样本量很小，只能用于检查真实 Q8 动态压缩机制。它们说明接口、索引和序列压缩能够运行，但不能支持精度结论，也没有 Q8-B 板端计时，因此不能称为已经获得加速。

### 5.4 BF16 同样退化，问题不只来自量化

我们把相同的 Token 掩码放回 BF16 Hugging Face 模型，空间任务仍然退化。因此 Q8 实验中的问题不能简单归因于 8 位量化或 GGUF 后端，Token 删除本身确实改变了模型依赖的空间表征。

### 5.5 连续 ROI 能明显减少 Vision 和 Prefill，但还没有通过精度门

在 32 图分层实验中：

- Dense 平均使用 278.1 个视觉 Token；
- 真值 ROI-only 平均使用 80.6 个，Token 比为 0.290；
- Grounding Mean IoU 相对 Dense 下降 0.0122，95% 置信区间为 [-0.0657, +0.0518]；
- Pointing PCK@0.1 相对 Dense 下降 0.0312，95% 置信区间为 [-0.1875, +0.1250]。

两个区间都跨过 0，而且下界超过预设的 -0.02 非劣界限，所以结论只能是“证据不足”，不能写成“精度基本不变”。

同一次空闲 A6000 测量中：

- Vision 约从 21 ms 降到 10 ms；
- LLM Prefill 约从 47 ms 降到 29 ms；
- Decode 基本没有变化；
- 应用 p50 延迟只下降约 7% 至 11%。

视觉阶段确实变快，但完整请求仍主要受 Decode 影响，所以视觉 Token 大幅减少没有转化成同比例的端到端收益。

### 5.6 固定使用 384 或 512 都不能同时满足预算和精度

在完整 192 图开发集上：

| 方法 | Token 比 | Grounding Mean IoU | 相对 Dense | Pointing PCK@0.1 | 相对 Dense |
| --- | ---: | ---: | ---: | ---: | ---: |
| Dense | 1.000 | 0.8103 | 0 | 0.6458 | 0 |
| ROI-384 | 0.342 | 0.7890 | -0.0214 | 0.5990 | -0.0469 |
| ROI-512 | 0.609 | 约 0.8164 | +0.0061 | 0.6250 | -0.0208 |

ROI-384 达到了 Token 不超过 50% 的预算，但两个任务都下降；ROI-512 精度更接近 Dense，却使用了 60.9% Token。因此没有一个固定分辨率同时满足预算和两项任务精度要求。

如果用真实答案为每张图选择 384 或 512，Grounding 可在 0.497 Token 比下达到 0.8452 Mean IoU，Pointing 可在 0.478 Token 比下达到 0.6615 PCK@0.1。这证明“每张图使用不同视觉预算”存在潜力，但我们尚未找到不读取答案的可靠选择器。

### 5.7 同样保留 34.2% Token，连续 ROI 远好于离散删除

在 192 图上把三种方法的最终 Token 数逐样本对齐：

| 方法 | Token 比 | Vision MAC 比 | Grounding Mean IoU | Pointing PCK@0.1 |
| --- | ---: | ---: | ---: | ---: |
| Dense | 1.000 | 1.000 | 0.8103 | 0.6458 |
| 连续 ROI-384 | 0.342 | 0.309 | 0.7890 | 0.5990 |
| layer5 L2 离散裁剪 | 0.342 | 0.482 | 0.5324 | 0.3438 |
| layer5 几何 Oracle 离散裁剪 | 0.342 | 0.482 | 0.5710 | 0.2708 |

L2 相对 Dense 的 Grounding 下降 0.2780，95% 区间为 [-0.3268, -0.2291]；Pointing 下降 0.3021，区间为 [-0.3750, -0.2292]。这是明确退化，不是样本波动。

普通 L2 只在 150/384 个任务样本中保留了目标中心。几何 Oracle 把目标中心保留提高到 372/384，并保留约 75.9% 的目标相交网格，但精度仍显著差于连续 ROI。

因此，离散裁剪失败不能只解释为“没有选中目标”。连续 ROI 还具有三项优势：保持局部二维邻域、把目标重新采样放大、保持模型训练时更熟悉的规则矩形序列。

基于这个结果，我们停止约 34% Token 预算的 post-layer5 离散裁剪，不再为它开发 FPGA Selector。

### 5.8 低分辨率自动 ROI 定位器的计算量够低，但定位不够可靠

自动 ROI 定位实验使用 192 张图、384 个任务，并执行按图分组的 5 折交叉验证。

| 方法 | Grounding 目标中心召回 | Pointing 目标中心召回 | Grounding 目标覆盖率 | Pointing 目标覆盖率 | Token 比 | 累计 Vision MAC 比 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 文本和图像特征余弦相似度 | 0.510 | 0.474 | 0.433 | 0.385 | 0.411 | 0.417 |
| 岭回归热力图和尺度头 | 0.849 | 0.828 | 0.735 | 0.729 | 约 0.424 | 约 0.432 |

这里的“目标中心召回”表示预测 ROI 是否包含真实目标中心；“目标覆盖率”表示真实目标框面积中有多少比例被预测 ROI 覆盖。

预设门槛是中心召回至少 0.95、目标覆盖率至少 0.85、Token 比不超过 0.5、累计 Vision MAC 比不超过 0.6。计算成本通过了，但定位没有通过。

分组结果进一步显示：

- 大目标中心召回为 0.9722，小目标只有 0.6912；
- 图像内部目标为 0.9615，靠近边缘的目标只有 0.8072。

这正是具身任务最不能忽略的情况：小零件、杯把、接触点和画面边缘目标更容易被低清 Scout 漏掉。按照预先设定的停止规则，我们没有继续运行完整 4B 模型，也没有打开校准集和测试集。

## 6. 现在最难的问题是什么

### 6.1 小目标和精细位置不能像分类任务那样容忍信息丢失

图像分类只要还能判断“这是一只杯子”就可能算正确；Pointing 和 Grounding 需要给出准确位置。少量边缘和局部纹理被删除后，类别可能仍然正确，但坐标已经超过 PCK 或 IoU 阈值。

### 6.2 选择 Token 所需的信息本身需要计算

在视觉编码器前几层做选择最省计算，但这些特征还不够理解任务；运行到后几层再选择更可靠，却已经支付了大部分视觉计算。增加一个更强的选择模型也许能提高定位率，但它可能把裁剪节省的时间全部用掉。

### 6.3 离散 Token 不是连续图像区域的等价替代

几何 Oracle 已经尽量保住目标，仍然远差于 ROI。这说明模型不仅需要“目标是否存在”，还依赖规则二维邻域、目标尺度、位置编码以及连续序列结构。对冻结模型直接做大比例离散删除，会产生明显的输入分布变化。

### 6.4 最终 Token 数不能代表总工作量

layer5 后保留 34.2% Token 时，前 6 个视觉层仍处理完整图像，所以 Vision MAC 仍有 48.2%。ROI-384 从输入侧减少区域，Vision MAC 可降到 30.9%。任何后续论文都必须同时报告裁剪位置、每层序列长度、累计 MAC 和实测延迟。

### 6.5 当前端到端瓶颈已经转向 Decode

ROI 能明显减少 Vision 和 Prefill，但 Decode 不变，因此应用延迟只改善 7% 至 11%。对于需要输出较长轨迹或解释文本的任务，Decode 占比还会更高。只优化视觉 Token 很难单独达到 333 ms 的高层决策目标。

### 6.6 FPGA 不能作为一个独立往返的“筛选服务”

80 组平台无关链路模型中，GPU→FPGA 选择→GPU 的外部往返方案没有一组优于纯软件压缩。FPGA 上的选择器只有与数据采集、预处理或后续算子形成单向流水，或者让状态长期驻留在 PL 中，才可能产生系统收益。

## 7. 还有哪些问题没有解决

1. 如何用很低的计算成本，把小目标和边缘目标的 ROI 中心召回提高到 0.95 以上？
2. 如何在保留连续二维结构的同时，把平均视觉预算稳定压到 Dense 的 50% 以下？
3. 如何让 384→512 的逐步细化复用已有特征，而不是把同一图像编码两次？
4. 对视觉骨干做裁剪感知微调或蒸馏，能否让模型适应稀疏 Token？目前实验主要使用冻结模型。
5. 不规则 Token 序列对 RoPE、MRoPE 和 DeepStack 对齐的影响边界还没有完全解决。
6. 是否可以用非自回归结构化动作头直接输出框、点和轨迹，从而减少当前占主导的 Decode？
7. 最终 AI 核心平台还未确定，跨设备带宽、共享内存、DMA 延迟和整机功耗还不能实测。
8. 当前没有实现 ZCU102 上的 Selector/ROI 控制器。软件精度门未通过前暂停 RTL 是主动决策。
9. 封存的 96 图校准集和 512 图测试集尚未使用，新方法必须先通过开发集门槛才能打开。
10. COCO 没有真实抓取点、可供性、轨迹和碰撞标注，当前结果不能代表机器人闭环成功率。

## 8. 这一阶段能够得出什么结论

本阶段没有得到可以直接写入 FPGA 的激进 Token 裁剪算法，但完成了三个重要判断。

第一，**L2@87.5% 可以保留为轻度裁剪基线**。它的 Token、Vision MAC 和 LLM Prefill MAC 分别约为 Dense 的 87.5%、89.7% 和 87.3%，96 图盲集点估计没有显示明显下降，但仍不能宣称统计无损。

第二，**把 layer5 后的离散 Token 压到约 34% 不可行**。普通 L2 和读取真值框的几何 Oracle 都显著损害 Grounding 和 Pointing。这条路线已经有充分理由停止，不应继续做 Selector RTL。

第三，**连续、任务相关的 ROI 比离散删除更有希望**。真值 ROI 和逐图分辨率 Oracle 证明了低于 50% Token 的潜在上界，但目前的低成本自动定位器对小目标和边缘目标不可靠，还不能部署。

从完整应用看，视觉 Token 裁剪只能解决 Vision 和 Prefill 的一部分开销。当前 A6000 测量中应用 p50 只下降约 7% 至 11%，Decode 已经成为更主要的问题。因此下一阶段不应继续盲目搜索相似的 Token 打分规则，而应优先验证任务感知的非自回归结构化动作头，并把 ROI-384、Dense 和 L2@87.5% 作为该方向的视觉输入对照。只有软件质量和端到端收益通过后，再决定哪些模块值得放到 ZCU102。
